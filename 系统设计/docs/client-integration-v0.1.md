## 3. 为什么先选 HTTP

HTTP 已有客户端 K 线调用线索，适合每个完整分钟运行一次模型。建议沿用客户端 3 秒刷新间隔，单连接、超时退避，先验证实时收盘数据及恢复能力。刷新间隔和性能门槛均是待确认建议。

WS 能补充报价可视化，但还缺可用握手、订阅响应及 K 线完整性证据；它不作为首版必备依赖。禁止运行中自动从 HTTP 切到另一个源。

行情分析端缓存是备选调查路线：沿用已有导出工具的行情区布局线索，但不能直接循环执行该脚本，因为脚本全文件读取且会覆盖输出。以后确需开发缓存适配器，应只读获准的行情区、检测写入中记录/环形覆盖/缓存品种改变，在本工作区保存结果。当前不开发这一分支，也不假设它比 HTTP 更新。

## 4. 复用模型的边界

模型工程：`D:\mycode\沧海易购1\market-direction-ml`。

| 现有代码 | 可复用部分 | 接入所需的最小处理 |
|---|---|---|
| `src/predict.py` | `load_bundle` 的模型路径/哈希检查；`predict_history`、概率及置信度逻辑 | 保留验证。来源绑定需经过明确批准的窄范围扩展，不能把 HTTP 冒称为旧 CSV 来源 |
| `src/data_loader.py` | 字段校验、开盘单价事件合并、available_at | 仅接收已确认完整根；原生时间和实际可用时间分别存储 |
| `src/labels.py` | `filter_bars`、`make_labels` | 三连后跳两根、跳后重计数、跨度按后续有效根；规则状态重放一致 |
| `src/features.py` | 39 个既有特征 | EMA 等依赖历史起点，不能仅截最后 64 根冒充完整重放 |
| 已有 `.venv` 和可信模型目录 | 本地依赖与冻结模型 | 不安装包、不搬动可信模型、不训练或改阈值 |

`predict_history` 当前要求来源字符串等于 bundle 中的 `supplied-20261028-native-csv`，直接传新 HTTP 来源会拒绝。这是应保留的边界。建议新增受审查的部署绑定记录：训练源哈希、实时源、品种、时间/单位映射、重叠对账证据、模型哈希；批准后才允许该绑定用于输入。对账不通过则停在观察/采集阶段，不能绕过校验，不能未经授权重训来消除问题。

现有预测输出的 `prediction_timestamp` 是**锚点 K 线可用时间**，不是程序真实发出预测的时间。新账本必须另存 `received_at`、`computed_at`、持久化后发布回执时间 `published_at`；所有前向判断使用真实发布证据。

该 API 的输出路径限制在原模型工程内。建议调用 `output=None`，由本工作区自己的 SQLite 保存返回结果；无需放宽既有输出路径限制。

本轮历史完整重放实际耗时 7.966 秒，返回 RULE_SKIP。它只验证旧接口及跳过分支，不能代表完整概率计算或端到端 p95。先按每根重放实现，实测不能满足发布期限时再针对状态/特征做增量处理，避免现在另造一套特征算法。

## 5. 最小系统与持久化

单个本地采集/预测/结算进程，复用现有 Python 环境，SQLite 为唯一统计依据，控制台显示当前状态。首版无新增网站、云服务、Redis 或交易能力。

启动时：验证部署/模型/源绑定→读取暖机历史并重放→记录本次前向观察起点。历史及断线补回数据只用于重建/结算，不补发过去的“实时预测”。

运行时：获取行情→校验身份/字段/时间→按源和品种去重、保留修订→确认已收盘→重放原规则/特征→产生预测→落库并取得发布回执→未来有效根到达后结算。存储失败不展示正式预测或更新统计。

收盘机制须先通过真实观测确定：接口若同时返回当前形成中根，可用后继区间出现等证据确认前根；若只返回收盘根，需要核实时间及服务器确认机制。两次相同值不能独自证明收盘；无法确认则 `FINALITY_UNKNOWN`，停止发预测。不得简单丢弃最后一根后，又把已经知道结果的预测算前向。

建议四张表：行情与修订 `bars`、不可改写的 `predictions`、可追溯修订的 `settlements`、源状态/跳过/缺数/发布回执 `events`。模型部署配置另存固定摘要。预测唯一键为部署+来源+品种+周期+锚点+h；锚点修订不自动生成第二条预测。输入及规则版本、模型哈希、特征摘要和源响应证据与每条预测关联。

行情、统计和修订分别保留。重新启动以账本和同一历史重放恢复，重放不重复发布。SQLite 提供一致性备份；进程停止后或通过 SQLite backup 接口备份，不能只复制运行中的主数据库文件遗漏 WAL。

## 6. 预测时间和命中率

首版建议定义为：上一根完整有效 K 线到达并验证后，对未来第 h 个有效收盘相对锚点收盘的方向预测。普通 h=1 时，取得上一根收盘通常已进入下一根，必须显示这个事实；不声称所有预测均在目标开盘前发出。若要求严格开盘前预测，需要另定发布机制和训练/评价边界，不把现有模型直接改名满足要求。

预测先落账 `PENDING`。目标有效根可验证完成后，收盘高于基准为 UP，低于为 DOWN，相等为 FLAT。方向一致为 HIT，否则 MISS；FLAT 独列。目标时间按实时因果规则事后解析，不预看未来跳过状态。概率相等仍沿用当前模型 `p_up>=0.5` 判 UP，不引入另一个工程的平手规则。

主命中率 = HIT / (HIT + MISS)。低置信度 `wait` 仍计入主统计；另列原阈值信号子集、覆盖率、上/下预测数、FLAT、PENDING、UNSCORABLE、规则跳过及源状态拒绝数。分母为 0 显示“暂无可计分样本”。同时给出 n 和 95% Wilson 区间；不是只显示一个百分数。

正式前向记录必须：在本次部署启用后真实发布、特征只到锚点、发布早于目标结果可用且满足固定延迟门槛。迟到输出保留为 `LATE/UNSCORABLE`；不能事后以正确结果放回分母。建议首版锚点至发布不超过 20 秒，具体可行性待实测及确认。

缺数不能默认为休市，也不能擅自让目标移到更晚一根。无法重建有效根序列则暂停、保留未结算，按固定到期规则转 UNSCORABLE。结果修订留存原结算与新版本，界面注明修订数，统计可按证据时点重算。历史、回放、实时及不同部署/源分别统计。

## 7. 下一步顺序

1. 确认本次需求/验收 v0.1 和品种，完成只读实际响应取样：验证名称/代码、时间、单位、完整性、缺数、真实刷新。通过对账才建立来源绑定。
2. 开发一条 HTTP 采集、一个冻结模型、一份 SQLite 账本和控制台。用固定回放夹具验证未来不可见、规则/重启一致、去重和结算。
3. 在真实交易时段连续前向观察，保存发布与收盘证据。真实实时链路及命中率通过独立验收后，才称已接通；模型效果单独报告。

现有历史报告为 55.68%（6,638 个计分样本），当前结论仍是未验证出稳定可用信号。该数字既不是本轮实时结果，也不作为未来准确率承诺。
